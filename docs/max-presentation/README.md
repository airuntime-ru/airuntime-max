# Презентация решения

Одна колода в двух форматах — под разные задачи:

| Файл | Что это | В git |
|---|---|---|
| `deck.html` | исходник PDF-версии, правки видны в диффе | да |
| `build-pdf.py` | печать `deck.html` в PDF, с токенами для жюри или без | да |
| `stamp-commit.py` | проставить commit hash на слайд 1 и пересобрать оба формата | да |
| `presentation.pdf` | PDF с заглушками на месте токенов | нет, генерируется |
| `presentation.jury.pdf` | PDF для сдачи: на слайде 1 рабочий токен бота | нет, **никогда** |
| `build-pptx.js` | генератор PowerPoint-версии | да |
| `presentation.pptx` | редактируемая колода для PowerPoint, без токенов | да |
| `capture-screens.py` | пересъёмка всех `shot-*.png` с настоящего мини-приложения | да |

PDF не хранится в git: Chrome растеризует градиенты и звёздное поле, и файл выходит за
лимит на размер бинарников. `.pptx` укладывается, поэтому лежит рядом с генератором.

## Пересобрать PDF

```bash
cd docs/max-presentation
python build-pdf.py                                   # presentation.pdf
MAX_BOT_TOKEN=... python build-pdf.py --jury          # presentation.jury.pdf
```

Задание требует на первом слайде рабочие токены и значения переменных окружения, а
в репозитории секретов быть не должно. Поэтому места под них в `deck.html` помечены
`data-secret="ИМЯ"`, и `--jury` подставляет значения из окружения (или из
`.secrets.env` рядом со скриптом) во временную копию, печатает её и сразу удаляет. Копия,
`.secrets.env` и `presentation.jury.pdf` в `.gitignore`; jury-PDF передаётся организаторам
напрямую. Сейчас помечены `MAX_BOT_TOKEN` и `OPENAI_API_KEY`; без второго на слайде
остаётся «по запросу» — сервис без ключа собирается шаблоном.

Chrome ищется в стандартных местах, другой задаётся через `CHROME=<путь>`. Страница
получается 960×540 pt, то есть ровно 16:9 при `@page { size: 1280px 720px }` и `.slide`
того же размера — если развести эти два значения, Chrome начнёт масштабировать и по
краям полезут полосы.

## Пересобрать PowerPoint

```bash
cd docs/max-presentation
npm install pptxgenjs --no-save
node build-pptx.js
```

Всё, что pptxgenjs нарисовать не умеет — градиенты, звёздное поле, скруглённые углы у
скриншотов, — приезжает картинками из `make-assets.py`:

| Файл | Где |
|---|---|
| `bg-cover.jpg` | фон обложки и финального слайда — его же берёт `deck.html`, поэтому обе версии открываются одинаково |
| `bg-dark.png` | «космические» слайды |
| `screen-*.png` | скриншоты со скруглёнными углами для рамок телефонов в `.pptx` (список — `SCREENS` в `make-assets.py`) |
| `card-owner-lead.png` | карточка заявки со слайда 10, вырезанная из экрана кабинета |
| `bubble-owner.png` | градиентный пузырь сообщения на обложке |
| `qr-bot.png` | QR-код на бота для финального слайда |
| `mark-airuntime.png` | знак AIRuntime, уменьшенный из `frontend/public/brand/logo-mark.png` |
| `mark-max.png` | знак MAX — официальная иконка с речевым пузырём, не кружок-заглушка |

Здесь же лежит `welcome.html` — исходник баннера на приветствии бота. MAX скачивает его сам
по адресу `https://airuntime.ru/brand/max-welcome-v7.jpg`, поэтому готовая картинка живёт во
фронтенде (новый путь — чтобы MAX не подставлял закэшированную старую версию). Холст 1280×720
(16:9): API MAX надёжнее принимает широкий кадр, чем 3:2. В пузыре чата картинка cover-кропается
и скругляется, поэтому текст и телефон сидят в центральной колонке с полями ~310px.

```bash
chrome --headless=new --force-device-scale-factor=1 --window-size=1280,720 \
  --screenshot=welcome.png "file:///$(pwd)/welcome.html"
# затем в JPEG 1280×720, качество 88: frontend/public/brand/max-welcome-v7.jpg
```

Размер тут часть задачи: pptxgenjs вставляет картинку заново на каждый слайд, где она
используется, а в репозиторий не проходят файлы больше 1000 КБ. Поэтому фоны — JPEG,
скриншоты — палитровые PNG, а `build-pptx.js` пережимает архив (сам pptxgenjs кладёт XML
слайдов без сжатия): `.pptx` весит около 520 КБ. Заодно он убирает повторные `<a:pPr>`,
которые pptxgenjs ставит перед каждым фрагментом абзаца, — PowerPoint их прощает, схема нет.

Проверка после сборки обязательна — pptxgenjs умеет выдавать XML, который PowerPoint
не откроет:

```bash
python <skills>/pptx/scripts/office/validate.py presentation.pptx
```

## Что нужно заполнить перед сдачей

- **Слайд 2** — `[Название команды]` и `[Участники и роли]`: квадратные скобки и пунктир
  оставлены намеренно, чтобы незаполненное поле нельзя было принять за готовый текст.
- **Слайд 1** — commit hash: одной командой `python stamp-commit.py` (берёт `HEAD`,
  правит `deck.html` и константу `COMMIT` в `build-pptx.js`, пересобирает оба формата).
  Делать это последним действием перед сдачей — жюри сверяет материалы с этой версией кода.
- **Слайд 1, `OPENAI_API_KEY`** — решить, отдавать ли жюри ключ LLM-шлюза. Если да —
  передать его `build-pdf.py --jury` так же, как токен бота.

Править нужно **в обоих** форматах: они собираются из разных исходников.

Токен бота попадает только в `presentation.jury.pdf`: в `deck.html` и `.pptx` на его месте
заглушка, потому что оба лежат в git.

## Структура

Колода разложена по критериям онлайн-этапа: после служебного слайда и обложки идут 11
слайдов — по одному на каждый критерий (5 продуктовых и 6 технических). На слайде критерия
пронумерованные блоки отвечают на пункты его чек-листа из задания, в том же порядке, чтобы
критерий оценивался по одному слайду. Слайд 3 — резюме и навигация по остальным.

| Слайд | Критерий | Чем закрыт |
|---|---|---|
| 1 | — (служебный) | ссылки, commit, переменные окружения, порядок проверки |
| 2 | — | название, команда «Тоталисты», три витрины в разных стилях |
| 3 | Качество презентации, 5% | проблема → решение → результат, ключевые цифры, навигация |
| 4 | Пользовательская ценность, 25% | сегмент, формула проблемы, результат, сравнение, факты и допущения |
| 5 | UX/UI, 20% | путь владельца и клиента на реальных экранах, состояния, отсутствие тупиков |
| 6 | Обоснованность, 15% | цепочка «проблема → механика → результат → метрика», MoSCoW, гипотеза |
| 7 | Масштабирование, 35% | ниши и регионы, условия адаптации, матрица рисков, диаграмма Ганта |
| 8 | Работоспособность, 30% | сценарий по шагам, функции и автотесты, QR на бота |
| 9 | Интеграция, 20% + бонус | поток данных, статусы, внешние интеграции, возможности MAX сверх минимума |
| 10 | Стабильность, 10% | повторы, реакция на ошибки пользователя, отсутствие тайм-аутов |
| 11 | Архитектура, 20% | схема компонентов, разделение модулей, «витрина — данные, а не код» |
| 12 | Безопасность, 10% | секреты, зависимости, модель доступа, данные, риски |
| 13 | Документация, 10% | воспроизводимость, README, ограничения, использованные источники |
| 14 | — | финал с QR-кодом на бота |

PowerPoint-версия (`build-pptx.js`) пока повторяет прежнюю структуру колоды; сдаётся PDF.

## Оформление

Колода оформлена как коллаборация двух брендов:

- **MAX / VK** — синий `#0077ff` и фиолетовый `#7b2cff`, официальный знак с речевым
  пузырём, «лестница» из пикселей как фирменный мотив, плоские светлые поверхности.
- **AIRuntime** — глубокий космос `#05070f`, звёздное поле (тот же SVG-тайл, что в
  `frontend/src/app/globals.css`) и настоящий логотип из `frontend/public/brand/`.

Связующий элемент — градиент MAX-синий → фиолетовый: он же в «галочке» надзаголовка,
в верхней кромке ключевых карточек и в номерах шагов. Тёмные «космические» слайды
(архитектура, масштабирование, источники) чередуются со светлыми — это ритм, а не декор:
на тёмных говорим про движок, на светлых — про продукт.

Обложка и финальный слайд стоят на одном фоне: космос AIRuntime, подсвеченный градиентом
MAX. На обложке продукт показан в одну строку: описание бизнеса → «Витрина готова» с
кнопкой «Поделиться ссылкой» → сама витрина на телефоне. Финальный слайд
замыкает колоду и даёт QR-код на бота — попробовать можно, не перепечатывая ссылку.

`print-color-adjust: exact` обязателен: без него Chrome печатает тёмные слайды белыми.

## Скриншоты

`shot-*.png` сняты с работающего мини-приложения при эмуляции вьюпорта 390×780 —
это настоящие экраны целиком, а не кадрированные куски: подрезанный скриншот читается
как сломанный слайд. Данные на экранах демонстрационные («Автосервис на
Лесной», «Пётр Клиент»), и слайд 5 говорит об этом прямо. Индикатор dev-режима Next.js при съёмке скрывается
(`nextjs-portal { display: none }`), иначе он запекается в каждый кадр. Пересъёмка — одной командой: поднять фронтенд (`npm run dev` в `frontend/`) и запустить
`python capture-screens.py`, затем `python make-assets.py`. Скрипт сам подменяет API и MAX
Bridge внутри браузера, поэтому в код продукта ничего временного не попадает. Демо-витрины для
обложки лежат в `demo_storefronts.py`.

## Проверка вёрстки

Слайды фиксированной высоты с `overflow: hidden`, поэтому переполнение не видно глазом —
оно просто обрезает контент. Проверять нужно в обе стороны: `.body` центрирует содержимое
по вертикали, и то, что в него не влезло, вылезает **и вниз, на футер, и вверх, на
заголовок** — именно так телефоны на слайде со сценарием однажды наехали на его название. Перед
пересборкой пройтись по `.slide` и убедиться, что:

- ни один потомок `.body` не начинается выше низа `.slide-head`;
- ни один текстовый блок, картинка или карточка не пересекается с `.foot`;
- на обложке и финальном слайде блоки не пересекаются друг с другом (исключение —
  ответ бота, который намеренно лежит на пустой нижней части телефона).

У картинок в рамках задан `aspect-ratio`, поэтому вёрстка не зависит от того, загрузился
ли скриншот, — и проверка честная даже на снимке страницы без картинок.
